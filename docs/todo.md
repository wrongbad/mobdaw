# To do

- **Drags share one local draft slot.** `store.setDraft` / `clearDraft` (`client/src/project/store.ts`) hold a single `Moving`, so two gestures at once (two fingers, a slider while a clip drag is held) overwrite and clear each other's draft; the loser's final value is still the one its own drop commits, but its preview vanishes. The draft of a left-edge MIDI trim also carries every note's tick, so it is as big as the clip and goes out through awareness every 50 ms. Fix if either bites: key the draft by gesture (merge them in `refresh`), and send a note offset instead of per-note ticks.

- **A cancelled loop take drops its undo step with `undoStack.pop()`.** The loop cancel in `client/src/audio/loopPedal.ts` (`restoreLoops`) restores the doc directly (untracked origin) and then pops the gesture's own step off `Y.UndoManager.undoStack` when it is still on top. The popped item is not released the way `UndoManager.clear` does, so the deleted Yjs items it referenced are kept until the doc goes (a small leak per cancel), and a loop that was replaced outright comes back with a new clip id. Fix if it shows: restore through a paused/untracked write from the start (never create the step), or clear the item with the manager's own API. (Pointer drags no longer have this: they write nothing until the drop.)

- **Resampler states are never flushed for denormals.** `dsp::resampler::Resampler::step` (used by the tape delay head and the looper heads) lets the modal state decay through the subnormal range when its input is silent; wasm has no FTZ. It is a bounded transient (thousands of samples) so it has not been seen to matter. If a long-session CPU spike shows up on a silent looper region, flush `s` every N steps (as `Svf` does).

- **Presets don't record the calibration they were tuned against.** The bore knobs (`breath`, `aperture`) are mapped through `bore_cal.rs`, so refitting the calibration silently changes how every tuned preset sounds (`client/src/content/presets.ts`, `engine/crates/dsp/src/bore_cal.rs`). Fix: stamp a calibration revision in `bore_cal.rs`, record it in each bore preset (`basedOn`/`rev` comment or field), and add a check that flags presets whose revision differs. See `docs/matching.md`, "Matched vs hand-tuned presets".

- **Effects that call `x()` / `fromX()` now track `pps` and `rate`.** They are signal reads since the scale mirror was removed (`client/src/ui/timeline.ts`), so any effect or memo that places something with them re-runs on every zoom step, whether or not it meant to. That is right for the lanes, but a heavy effect that only wants the zoom once should read them inside `untrack`. Check when a zoom drag feels slow with many clips.

- **A clip moved to another lane is torn down and rebuilt there.** `<For>` is keyed per lane (`client/src/ui/clips.tsx`), so a lane change disposes the old clip element (its waveform canvas and MIDI preview included) and draws a new one; nothing was seen to glitch (the waveform redraws from cached peaks). Fix only if it shows: hold the clip elements in one keyed map above the lanes and reparent them.

- **"save a copy" appears on any write to a snapshot's document, not only the user's edits.** `mountTimeline` (`client/src/ui/timeline.ts`) sets `edited` on every `doc` update after the first sync, so an automatic write (a take or sample status, a future migration) would show the button and the "changes stay on this page" hint for a visitor who changed nothing. Nothing writes today that the user didn't cause; if one does, track edits by origin (the user's edits carry `null` or the undo manager) or compare against the snapshot's state vector.

- **The admin `passwd` command ends sessions but not open collab connections.** `scripts/admin.ts` runs in its own process and deletes the user's `sessions` rows (`revokeSessions`), but it has no handle on the server's Hocuspocus connections, which were authenticated at connect time and stay open until they drop or are closed by an access change (`kickUser` in `server/src/collab.ts`). The user can keep editing over an old socket after a password reset. (API tokens are handled: `passwd` deletes them and the 60-second `enforceReadOnly` pass closes connections whose `tokenHash` is gone, and `hub.sweepRevoked` ends agent presence; only session-token sockets are left.) Fix: have the 60-second `enforceReadOnly` pass (`server/src/main.ts`) also close connections whose user has no live session, which needs the session or token hash stored on the connection context at connect.

- **Already-deployed clients have no schema-version guard.** Before v4 nothing checked `meta.schemaVersion > SCHEMA_VERSION`: an old tab still open (or cached) after the v4 migration will write v3-shaped MIDI clips (`start`/`bpm`/`ppq`, no `startTick`) into a v4 doc, and other clients will misplace them. `migrateToV4` re-converts any legacy-shaped clip (and its notes) it finds on the next open, using the current map, but until then they play at wrong times and the old tab keeps writing. Current clients refuse to touch a doc from the future (`isFutureDoc` in `shared/src/schema.ts`; the migrations and `sweepOrphans` skip it, and the UI must open such a doc read-only). Fix: ship the guard, bump `SCHEMA_VERSION` only after the old clients age out, and have the server reject Hocuspocus writes from a client whose handshake version is older than the doc's (`server/src/collab.ts`).

- **A v3 MIDI clip that straddles the end of a leading free region migrates slightly off.** `migrateToV4` scales a clip's ticks by one factor (the tempo where it starts), so a clip that starts before the click track's start and plays past it (the tempo changes under it) lands its late notes at the wrong samples. Rare (needs MIDI before a click that starts late); fix by splitting such a clip at the boundary during migration.

- **MIDI file import snaps tempo changes to bar lines and turns tempo ramps into steps.** `smfRegions` (`client/src/content/midifile.ts`) puts each tempo event on the nearest bar line (a change mid-bar moves up to half a bar) and a file that encodes a ritardando as dense tempo events becomes one region per bar, not a `rampTo`. Fix: detect runs of monotonic tempo events and write them as a ramp region; split a bar only if free/odd bars are ever supported.

- **Snapping in a looping MIDI clip follows the first pass.** The piano roll and drum grid (`client/src/ui/noteEditor.ts`, `drumGrid.ts`) snap clip-local ticks to the map's grid at `clip.startTick`, so when `loopTicks` is not a whole number of bars the repeats fall on different beats of the grid than the pass the notes were drawn on (the repeats are only drawn, never edited). Fine for whole-bar loops, which are the normal case.

- **A tempo change re-bakes all MIDI.** `Bridge.rebakeAll` (`client/src/audio/bridge.ts`) runs on every `regions`/`meta` change, recomputing the baked window (120 s) of every MIDI clip and the click, and sending each engine note that moved. Tempo is only set from the ruler dialog today (one write), so it happens once per edit. If a tempo drag is ever added it must follow the other drags (a draft in `Moving`, one write on release, see `client/src/project/draft.ts`) or `rebakeAll` must be throttled to ~20 Hz with a trailing call.

- **Anything that drives the engine without the Bridge must set the baked window.** MIDI exists in the engine only inside `Bridge`'s window (`setWindow`, moved by `play`/`seek`/position reports/`setCycle`). A path that calls `engine_play` or `engine_seek` directly (the offline render does, after `bridge.setWindow(from, end)`) hears silence for MIDI outside the default `[0, 120 s)` window. New offline paths must call `setWindow` first.

- **The ruler menu and dialogs read the map when opened, not live.** `ui/rulerMenu.ts` builds its entries from `getRegions(doc)` at click time and the tempo dialog fills its fields once; a collaborator editing the same region while the dialog is open is overwritten on "set" (last write wins, still one consistent partition). Acceptable; fix only if it bites by re-reading the region on submit and warning when it changed.

- **History entries are only as durable as the process.** `server/src/history.ts` writes each entry to SQLite synchronously inside the `afterTransaction` handler, but the doc itself is stored by Hocuspocus on its debounce, so a crash can leave rows in `history` whose edit never reached the stored document (a revert of such an entry skips every field as "changed since" or recreates something that never existed). Loading a doc reconciles the summary array with the rows, not the rows with the document. Fix: store the document's state with the entry (or write the row from the `Database.store` hook) if crashes ever show up.

- **The history mirror is rebuilt from the stored doc whenever a document loads.** A document unloads when its last connection leaves and the mirror goes with it; reloading rebuilds it from the stored state, so diffs stay correct, but a change that arrives between the stored state and the unload (a crash) is attributed to nobody. Also, `attachHistory` clears the doc's `history` array when the project has no rows (that is how a copied project drops the original's log), so restoring the `history` table from backup without its documents, or the reverse, silently empties the panel.

- **Revert and restore re-create entities field by field and trust the patch.** A restore (`restoreTo`) rolls back whole entities to their state before the first later entry; a child created after the restore point whose parent is restored away (a note in a clip that was deleted at the restore point) is only removed because its own entry is in the range. A pruned entry (older than the last 2000) breaks that chain: restoring to the oldest kept entry cannot undo what an entry before it did. The client's `sweepOrphans` cleans up dangling children, which hides it.

- **Agent ops clone the whole document per batch.** `applyAtomic` (`server/src/agentOps.ts`) copies the live Y.Doc into a scratch doc (`encodeStateAsUpdate` + `applyUpdate`) on every `apply_ops` call to get all-or-nothing, so a call costs O(document size) in CPU and memory, on the event loop. Fine for songs; a project with a lot of history in its Yjs state (or many agents batching quickly) will notice. Fix: validate against the live doc without writing (a dry-run mode in `run`), or keep a long-lived scratch doc per project that is updated from the live doc's updates.

- **Agent event cursors and buffers die with the agent's presence.** `server/src/agentHub.ts` keeps a project's event buffer (500 events) only while some agent is active there; after the idle timeout, or a server restart, a returning agent's old cursor yields `gap: true` and it must re-read state and chat. Cursors are one counter per process, so a cursor from before a restart can be larger than the new counter (treated as "from now"). Anything that wants a durable event log (webhooks, an agent that sleeps for hours) needs it written somewhere real.

- **A chat mention of an agent only counts while the agent is present.** `@k(api)` is parsed against the handles of the members plus whoever is in the awareness (`client/src/ui/chat.tsx`, `AgentHub.handles`), so a message typed while the agent is idle stores no `mentions` for it. `events` and `GET chat` re-parse the text for `mentionsMe`, so an agent that polls sees it, but any other consumer of `ChatMessage.mentions` (an unread badge for the api identity) does not.

- **API-token WebSocket clients assert their own awareness and chat names.** A token may connect to the collab socket as "k (api)" (`onAuthenticate` in `server/src/collab.ts`), but awareness and chat authorship are written by the client, exactly as for humans: such a client can post chat or draw a dot under another name. The HTTP agent API and MCP do not have this (the server writes the name).
